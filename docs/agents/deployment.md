# Deployment and Runtime Captures

Part of the project guide. The short index and the must-not-break rules are in [AGENTS.md](../../AGENTS.md).

## Deployment System (Virtual / usvfs VFS)
- Deployment is **virtual**: enabled mods are mapped over the game tree by **usvfs** (Mod Organizer 2's User-Space Virtual File System) at Launch Game, so there are no symlinks, no full copies, no admin/UAC, and it works cross-drive.
- Bootstrap exception: import-time proxy/loaders must be visible before the process starts. `IPC.LAUNCH_GAME` physically stages only path-based bootstrap candidates (top-level `bin/x64` DLL/ASI/INI/config files and direct `bin/x64/plugins` DLL/ASI/INI/config files) before mounting usvfs; all remaining mod payload stays virtual. CET's `version.dll` + ASI loader is just one example of this rule.
- **Bootstrap staging is crash-safe via a persisted manifest** (`vfs-bootstrap-staged.json` in `userData`): the staged entries/temp dirs/override dirs are written after staging and removed by `cleanupStagedBootstrapFiles`. If a session ends without running its cleanup (crash, kill, or quit while the game is attached), `sweepLeftoverBootstrapStaging()` replays it at the next startup (deferred while the game runs), and the next `LAUNCH_GAME` folds any leftover manifest into its fresh staging lists (`mergeStagedBootstrapEntries`/`mergeStagedTempDirs`) so previously copied loaders are still removed on that run's game exit. Do not go back to memory-only staging tracking. The status rules live in the pure `src/main/bootstrapStaging.ts` (`isHyperionStagedEntry`, `mergeStagedBootstrapEntries`, covered by `tests/bootstrapStaging.test.ts`): the launch tracks BOTH `copied` and `already-present` entries from fresh staging, and the merge keeps both, so a loader left by an earlier session is removed on this session's game exit.
- **Bootstrap cleanup removes BOTH `copied` AND `already-present` staged entries, with NO match guard.** `stageBootstrapFile` marks an entry `copied` (Hyperion created the file), `already-present` (a prior session's identical staged loader still sits there - it byte-matched the library source at staging time), or `existing-kept` (a DIFFERENT pre-existing file the user owns - never touch). `cleanupStagedBootstrapFiles` deletes `copied` and `already-present` outright (both are Hyperion's staged loaders) and leaves `existing-kept`/`error`. Do NOT reintroduce a "still matches the library source" guard on removal: a loader whose source was updated/uninstalled, or that the game touched at runtime, would then be skipped and orphaned - a stray `.asi`/`.dll` left in `bin/x64/plugins` crashes a mod-free launch. Cleaning only `copied` (the original bug) let a loader that survived one dirty exit become `already-present` and pile up forever. The user's own file is safe because a path Hyperion never staged is never in this list, and a matching-path-but-different file is `existing-kept`.
- **"Game closed = game folder clean."** After files are migrated/removed on unmount, `pruneEmptyModFrameworkDirs` (`src/main/vfsFrameworkCleanup.ts`) drops any EMPTY framework directory trees the session left behind (under `bin/x64/plugins` and `red4ext` - neither exists in a vanilla install). It is also run on the zero-mod direct launch so a vanilla start is clean. It uses `fs.rmdirSync`, which only removes EMPTY dirs, so a mod the user installed OUTSIDE Hyperion (real files present) is never deleted. Pure and unit-tested (`tests/vfsFrameworkCleanup.test.ts`).
- **REDmod support runs entirely inside the VFS.** REDmods only load after `tools/redmod/bin/redMod.exe deploy` compiles the `mods/` tree into `r6/cache/modded` AND the game launches with `-modded`. When enabled mods include REDmod content (`modHasRedmodContent`, deploy paths under `mods/`), `IPC.LAUNCH_GAME` runs `redMod.exe deploy -root=<gameRoot>` as a **VFS-hooked process after mounting** (`deployRedmodsUnderVfs` in `index.ts`): it reads the *virtual* `mods/` tree and its `r6/cache/modded` writes are redirected into the Runtime Captures overwrite folder - the real game dir stays clean - then the game is launched with `-modded`. The hooked launch is detached (no exit code), so completion is polled by PID (main thread never blocks; cancellable; 8-min timeout) and success is verified by fresh output in the captured `r6/cache/modded`. The deploy runs in a VISIBLE console window (Vortex-style live output): cmd builds the exact raw argument shape redMod's parser expects (`-root="path"` with quotes around the path only - PowerShell's own arg re-quoting yields `"-root=path"`, which redMod rejects as "No root specified") and pipes merged output (`2>&1` BEFORE the pipe, so no red NativeCommandError wrapping) into `powershell -Command "$input | Tee-Object ..."`, mirroring every line into `redmod-deploy.log` - which powers the launch-card narration (the poll loop streams the newest log line into the card detail) and the success check. Tee-Object writes UTF-16LE, so `readDeployLog` decodes by BOM. NEVER pass `capture: true` to `launchHookedProcess` for a long-running child: the bridge's ReadFile loop is synchronous and freezes the entire main process until the child exits. A fingerprint (`redmodFingerprint.ts`, stored in `redmod-deploy-state.json` in `userData`) of the enabled REDmod set plus the game build skips the slow deploy when nothing changed. The build identity is the size and modified time of `Cyberpunk2077.exe` and `redMod.exe`, with no hardcoded game version, so a patch forces a redeploy on its own. The stored state is dropped before each deploy and written only after one finishes, so a cancelled or crashed run's partial output is never reused; **Clear captures** wipes the compiled output, which auto-forces a redeploy on the next launch. Deploy failure (or missing REDmod DLC) degrades to a normal launch without `-modded` plus a warning log. **Load order between REDmods follows the library**: the deploy passes an explicit `-mod=` list (`getRedmodFolderNames` per enabled mod, ascending `order`, later entries win - matching Hyperion's higher-#-wins rule; duplicate ids keep their last slot), the fingerprint includes that list so a pure reorder redeploys, and a failed `-mod` attempt retries once with redMod's default (all mods, alphabetical) so a syntax mismatch on some tool version never blocks the launch.
- **VFS lifecycle guards**: `IPC.LAUNCH_GAME` is re-entry-guarded (`vfsLaunchInProgress`, plus an "already running" check against `vfsProcesses()`/`tasklist`) because a second `mountVfs` resets the shared usvfs state under an attached game. `before-quit` only unmounts when no process is attached to the VFS - clearing virtual mappings under a running hooked game makes every mod file vanish mid-session; when attached it leaves the VFS resident and lets the startup sweep / next launch reconcile. The game-exit monitor requires **two** consecutive missing checks (8 s) before unmounting so a transient `tasklist` failure can't tear the VFS down mid-game. All `tasklist`/`taskkill` `exec` calls pass `windowsHide: true`.
- Native bridge lives in `native/usvfs-bridge/` (see its README) and is loaded via `src/main/vfsBridge.ts` (`loadVfsBridge()`/`isVfsAvailable()`). Built with `npm run build:native`, bundled to `process.resourcesPath/usvfs` for packaged builds. usvfs binaries are fetched by `npm run fetch:usvfs` (pinned v0.5.7.2, gitignored under `vendor/`).
- `buildEnabledModLinks(gamePath, libraryPath)` in `modManager.ts` computes the ordered `{source, dest}` pairs from enabled mods (load order = ascending priority, later overrides earlier). `IPC.LAUNCH_GAME` in `index.ts` calls `mountVfs(links)` → `launchHookedProcess(Cyberpunk2077.exe)` and unmounts on game exit / kill / quit.
- Enable/disable/install/reorder only update `_metadata.json`; the VFS reflects them on the next launch. `redeployEnabledMods` just refreshes library state (deployment is virtual, so nothing is re-staged), and the `deployedPaths` field is unused.
- The `createSymlink`/`safeRemoveLink`/`isLink` primitives in `fileUtils.ts` are not part of deployment (which is virtual). They remain only for a possible one-time cleanup of legacy symlinks a pre-VFS elevated run could have left in the game folder.
- Runs as `asInvoker` (no UAC elevation). usvfs does not require admin - it uses user-space API hooking. This also allows `nxm://` protocol forwarding to work correctly (a non-elevated browser can hand links to a non-elevated app).
- Conflict detection only considers **enabled** mods - both in `modManager.ts` and `modConflictState.ts` (renderer). It reads game-target paths via `getTrackedDeploymentPaths`, which computes them from each mod's files.

## Runtime Captures
- When mods run under usvfs, tools like CET write files physically into the game directory (keybindings, logs, generated configs). On game exit these are migrated out of the game folder into a **Runtime Captures** folder that lives beside the Mod Library (e.g. `Documents/Hyperion/Overwrite`), so the game directory stays clean between sessions.
- `migrateVfsPhysicalResidue` in `src/main/index.ts` handles migration: `collectVfsResidueDirs` identifies directories that may have runtime writes (plugin dirs, red4ext/logs), then `migratePhysicalResidueDir` processes each file - removing it if it matches the mod's source file exactly, or moving it to Runtime Captures if it was modified at runtime.
- `cleanVfsOverwriteVolatileFiles` removes log files from Runtime Captures after migration (logs are regenerated on every launch and don't need to persist).
- On the next launch, Runtime Captures files are mounted back as VFS read overlays via `buildVfsOverwriteReadLinks`, so CET keybindings and other settings persist across sessions. `usvfsVirtualLinkFile` requires the destination's parent directory to exist at least virtually, and `usvfsVirtualLinkDirectoryStatic` only materializes directories that exist in a mod source - so captures whose parent folder is created at runtime (e.g. `red4ext/plugins/Codeware/Persistent`, `r6/storages/RedscriptConfigFramework`, `bin/x64/plugins/address_library`) have no virtual parent and their read link fails. `buildVfsOverwriteReadLinks` therefore materializes the captured file's full missing ancestor chain (every directory level up to the first one that exists physically in the game tree) from an empty real dir, shallow-to-deep, before linking the captured file - materializing only the immediate parent is insufficient when several levels are runtime-created (e.g. both `r6/storages` and `RedscriptConfigFramework`). Empty-dir links never hide files because usvfs merges directory links rather than replacing them. A final dedup pass in `IPC.LAUNCH_GAME` (keyed on source/dest/dir/createTarget) runs over the fully assembled link list right before `mountVfs`, since usvfs reports repeated identical links as failures. The Overwrite folder is a single always-mounted catch-all: `buildVfsOverwriteReadLinks` mounts **everything** in it regardless of which mods are enabled - captures are never filtered, parked, or moved based on enable/disable state.
- **Close Game timing**: `IPC.KILL_GAME` waits 1.5 s after `taskkill` before running residue migration - `taskkill` completes the command before the OS fully releases file handles, so an immediate migration races against locks.
- **Deleted-mod capture cleanup** (`src/main/vfsOverwriteCleanup.ts`): the Overwrite folder is a single always-mounted catch-all - captures are **never** moved, parked, hidden, or filtered based on enable/disable state. Do NOT attribute a shared framework folder like `cyber_engine_tweaks/` to one mod - many mods write there, so per-mod parking of shared captures is fragile. The ONLY automatic cleanup is removing a *deleted* mod's leftovers, and it is deliberately conservative:
  - `captureOwnerFolder(relPath)` maps a path to its per-mod *slot* - but ONLY under the strict one-folder-per-mod roots `bin/x64/plugins/cyber_engine_tweaks/mods/<X>` and `red4ext/plugins/<X>` (returns `null` for anything else, including the root of a framework folder, so framework-root and shared captures are never attributed to a single mod).
  - `sweepOrphanCaptures(overwritePath, liveOwners)` deletes captured files whose per-mod slot isn't owned by any installed mod, and prunes emptied parent dirs (never the Overwrite root). `cleanDeletedModCaptures(libraryPath, remainingMods, window)` (in `modManager.ts`) builds `liveOwners` from the remaining mods' `getTrackedDeploymentPaths` via `captureOwnerFolder` and calls the sweep. It runs in exactly ONE place: the `IPC.DELETE_MOD` handler, after a mod's folder is removed (passing the fresh pre-deletion scan minus the deleted mod). Enable/disable/launch do NOT touch captures. Because attribution is limited to per-mod slots, deleting a mod can only ever remove files in that mod's own private folder - never another mod's data or a framework root.
  - `getOverwritePathForLibrary(libraryPath)` computes the Overwrite path and MUST stay in sync with `getVfsOverwritePath` in `index.ts`. The backlog of captures from already-uninstalled mods is cleared manually via **Settings → Clear captures**.
- Exposed in **Settings > General** as a "Runtime Captures" card with file count plus "Open folder" and "Clear captures" actions. The count reflects everything in the Overwrite folder (it is a single catch-all, not filtered by enabled state). `Clear captures` wipes the whole folder - the manual way to manage accumulation. It does not belong in Settings > Paths because it is automatic runtime output rather than a user-chosen path. Intentionally absent from the Library toolbar - the system is fully automatic.
