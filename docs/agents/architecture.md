# Architecture

Part of the project guide. The short index and the must-not-break rules are in [AGENTS.md](../../AGENTS.md).

## Architecture Notes
- Main window stays hidden until the renderer sends IPC.APP_READY.
- Splash is handled by the main process. Do not add a second renderer splash.
- Native Cut/Copy/Paste/Select All on editable fields and selected text is wired in the main process via `attachEditContextMenu` (the `webContents.on('context-menu')` handler in `createMainWindow`, `index.ts`) - Electron shows no edit menu by default. It returns early for non-editable, non-selection targets so renderer-side custom menus (library rows, etc.) are unaffected. Do not add a duplicate renderer-side copy/paste menu.
- **Renderer lockdown.** The preload bridge (`src/main/preload.ts`) only forwards channels in the `IPC` map (plus the three `window:*` send channels) - add new channels to `IPC` in `src/shared/types.ts` or the bridge throws `Blocked IPC channel`. An app-wide `web-contents-created` guard in `index.ts` denies every `window.open`/`target=_blank` (https links go to the system browser via `shell.openExternal`), blocks `will-navigate` to anything but the app's own page (`isAppRendererUrl`), and blocks `<webview>`. DevTools (`DEVTOOLS_ENABLED`) are on in dev and OFF in packaged builds, unless the app is launched with `HYPERION_DEVTOOLS=1` for diagnostics. `IPC.OPEN_PATH` opens **directories only** (`shell.openPath` on a file would launch it, e.g. an `.exe`); reveal files with `IPC.SHOW_ITEM_IN_FOLDER`.
- Settings, mod scan, path validation, install/reinstall, and updater all flow through IPC. **`SET_SETTINGS` takes a PARTIAL** and the main process merges it over the persisted settings (single source of truth) - the renderer slice sends only the touched fields. Never send a full renderer-side settings copy: a stale/empty in-memory value (the Nexus API key before hydration bit us twice) would silently overwrite disk. The Nexus key field holds only a NEW key being typed (the stored key never reaches the renderer - see nexus.md → API key security), auto-saves only after a real user edit (`nexusKeyTouchedRef`) with a non-empty value, and the main process logs a warning whenever a stored key is cleared by a save.
- Mod library scan must ignore symlinks (they are deployment artifacts, not source files).
- Installed mod metadata stores sourcePath/sourceType so reinstalls can reuse the original source.
- Mod folder names preserve spaces and hyphens - `sanitizeFolderName` only strips filesystem-invalid characters (`<>:"/\|?*`), it does NOT replace spaces with underscores. Mods are keyed by `uuid`/`folderName` (synced to the real on-disk folder during scan), so older mods installed with `_`-style folders and newer space-style folders coexist with no migration. Do not reintroduce underscore folder names or batch-rename existing folders.
- Renaming a mod or separator (`IPC.UPDATE_MOD_METADATA` in `modManager.ts`) renames its on-disk folder to match the new display name and updates `folderName`. Mods use `getUniqueModFolderName`, separators use `getUniqueSeparatorFolderName` (both sanitize + de-duplicate with a numeric suffix). Deployment is virtual, so renaming the source folder is safe - the VFS recomputes links from `folderName` on the next launch.
- Installer extraction temp dirs live in `app.getPath('temp')/Hyperion/installer` (created via `createInstallerTempDir`/`removeInstallerTempDir` in `installer.ts`), NOT inside the mod library. `cleanupInstallerTempDirs(settings)` runs on app launch and `before-quit` to remove orphans, and also sweeps legacy `_tmp_*`/`_tmp_fomod_*` folders that older builds left in the library. Never recreate temp dirs inside `libraryPath`.
- **Slim renderer payloads.** Bulk mod lists cross IPC through `toRendererMod` (SCAN_MODS / RESTORE_ENABLED_MODS): `files` is emptied and `emptyDirs`/`hashes`/`archiveResources`/`deployedPaths` are stripped, with a main-computed `trackedResourceCount` added so the renderer's optimistic conflict recompute (`modConflictState.ts`) keeps the exact "fully redundant" denominator (it falls back to deriving keys locally for mods that still carry arrays - single-mod IPC results stay FULL: `REFRESH_MOD_FILES` and `MOD_TREE_*` feed the details Files tree and must keep `files`). **The renderer's `scanMods` merge carries `files`/`emptyDirs` over from the previous store entry when the incoming slim mod has none** - without it, any bulk scan landing while a details panel was open (e.g. the library watcher reacting to a tree create/rename) wiped the visible Files tree; `DetailPanel` additionally re-runs `refreshModFiles` on `LIBRARY_CHANGED` so the open tree stays live against disk. The conflict pass reads deploy paths via `getNormalizedConflictPaths`, backed by a WeakMap keyed on the (cache-stable) meta object. Renderer callers of `UPDATE_MOD_METADATA` must keep sending NARROW patches (`{ name }` etc.) - spreading a slimmed store mod into updates would wipe the on-disk `files`.
- **Metadata read cache (scan scalability).** `readMetadata` caches the composed meta (metadata + sidecar) per mod dir, validated by the **on-disk identity (mtimeMs + size) of both `_metadata.json` and `_archive_resources.json`** - so a scan of an unchanged 2k-mod library is ~2 stats/mod instead of 2 reads+parses/mod, while out-of-band writes (raw category write in `nexusDownloader`, sidecar unlinks, Explorer edits) invalidate naturally. **Invariant: the cached object is shared - mutate a returned meta ONLY if you persist via `writeMetadata` right after** (it re-stamps the cache); `writeArchiveSidecar` invalidates its dir's entry. `findModDir` keeps a uuid→dir hint (validated on use) to skip the full library walk. Similarly, `nexusDownloadRegistry` holds the registry in memory with an O(1) path index - do NOT reintroduce the per-lookup disk re-read/full prune (the Downloads refresh does one lookup per archive; pruning happens at write points and validates only matched records).
- **Mod file-list freshness.** Routine `scanMods` reuses each mod's stored `files` for speed and only re-walks a mod's folder when `refreshFileMetadata: true` is passed (so it never re-walks 100+ mods on every scan/conflict pass). Two paths keep the list honest about disk: (1) `IPC.REFRESH_MOD_FILES` re-reads one mod's files/type/size on demand - the renderer's `refreshModFiles(uuid)` fires it from `DetailPanel` when a mod's details open, so files added/removed in the folder via Explorer appear in the Files tab; (2) a recursive library watcher (`startLibraryWatcher` in `index.ts`, mirroring `startDownloadsWatcher`) emits `IPC.LIBRARY_CHANGED` on external changes, and the renderer re-scans with `refreshFileMetadata: true`. The watcher **ignores `_metadata.json`/`_archive_resources.json`** (Hyperion's own writes) so a refresh that rewrites them never loops; it re-points on `SET_SETTINGS` and tears down on `before-quit`. `fs.watch(..., { recursive: true })` is Windows/macOS-only - the `try/catch` makes a Linux dev env degrade gracefully to the on-open refresh.
